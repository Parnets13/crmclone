# Sales Order promise-stage provenance on Dealer Invoices

The change records each linked Sales Order line’s required sequential promise stage on the corresponding Dealer Invoice line, separate from the invoice’s live required stage. Backend canonicalization derives the snapshot from the exact linked line and clears it for standalone invoices; persistence and response paths carry it through create, edit, and detail views. Invoice discount changes recalculate only the live stage, and legacy invoices without a snapshot now display `Not recorded`. No blocking concerns remain.

**Verdict**: APPROVED

## High-level view

Linked lines use `sourceSalesOrderLineId` as their authority. Unknown, repeated, product-mismatched, and ambiguous duplicate-product identities are rejected rather than selecting the wrong source line.

Canonicalization copies `sourceSalesOrderRequiredSequentialStageRatePercentage` from that exact Sales Order line and overwrites standalone submissions with `null`. The schema persists it, and invoice responses do not project it out.

Frontend previews and the model pre-save hook update only `requiredSequentialStageRatePercentage`. The source field is absent from discount stages, GST, line amounts, and invoice totals.

Create hydration shows the selected Sales Order line’s stage; edit and detail views show the persisted snapshot. Missing or invalid snapshots resolve to `Not recorded` without consulting the live invoice stage.

## Exact Sales Order line identity controls provenance

`buildSalesOrderLineMatcher` resolves `sourceSalesOrderLineId` against the Sales Order line `_id`, verifies its product, and consumes each source line once. Product-only matching is rejected when the same product occurs on multiple lines. The canonical result takes both identity and source stage from the matched line, ignoring client provenance.

The frontend sends each selected Sales Order product line `_id` as `sourceSalesOrderLineId` but does not submit the source-stage value. Approval replays canonicalization and rejects missing or duplicate source identities before financial side effects.

## Standalone clearing and response persistence

Standalone canonicalization sets the source field to `null` after spreading submitted data, preventing spoofing. The nullable 0–100 schema field survives create, draft update, approval replay, list, and detail paths; none excludes it from responses. Create hydration uses the Sales Order line value, while edit hydration and saved detail rendering use the persisted invoice value.

## Live invoice recalculation remains financially isolated

`applySequentialDiscountPreview` and the model pre-save hook recalculate `requiredSequentialStageRatePercentage` without assigning the source snapshot. A repository-wide reference trace finds the source field only in schema, canonicalization, hydration, edit mapping, and display code—not in stage construction, discounts, GST, one-time increases, line totals, or aggregate totals.

## Legacy snapshot display

`getSourceSalesOrderPromiseStage` reads only `sourceSalesOrderRequiredSequentialStageRatePercentage`; missing, null, empty, non-numeric, negative, and over-100 values return `null`. Create/edit and saved-detail displays render that as `Not recorded`, while the live field remains separately labeled as the required next stage.
