# Rolling absence review and multi-session face attendance

The change replaces the month-bound absence review window with an inclusive IST rolling cutoff and adds face-driven IN/OUT selection from today’s session state. The date utility, cron, pending query, action guards, and displayed per-record deadline use the same 15-day lower boundary, while the frontend refreshes today’s attendance before opening the camera and again before submitting. The cutoff simulation passes and the frontend production build succeeds. Three concrete implementation gaps and one remaining concurrency window should be fixed before shipping.

Watch for: **confirmed** expired unresolved `none/null` absences are omitted rather than settled by the new list catch-up; **confirmed** face punch-outs are still stored with `source: "web"`; **confirmed** an in-flight automatic face scan can submit after the dialog closes; **likely** the refresh-then-write sequence can still race a concurrent biometric/web write.

**Verdict**: NEEDS_CHANGES

## High-level view

The policy boundary is calculated from IST midnight: on September 2, August 18 remains reviewable and August 17 expires. The deadline for August 18 is the end of September 2, so the modal shows the final reviewable calendar date. The “This Month” preset sends the current month’s first day through yesterday, while the renamed default pending preset represents the rolling review window.

Cron settles expired `pending` rows with Unpaid Leave, `unexcused`, and the normalized company multiplier. The new list-side catch-up performs the same transition only for literal `pending` rows even though the pending list also treats `none/null` as pending, leaving a missed-cron backlog hidden and unresolved.

Face attendance derives the next action from open sessions and refreshes before camera start and after matching. The second refresh is not coupled atomically to the mutation, so a punch arriving between those requests can still interleave with the selected action.

The face component clears its success timer on unmount, but an automatic detection already awaiting face-api can finish after cleanup and create a new timer. Punch-in now distinguishes face from manual source, while punch-out continues to label both paths as web.

<details><summary>Details</summary>

## Expired unclassified absences disappear from review without transitioning

The new GET catch-up updates only rows whose stored `reviewStatus` is exactly `pending` (`crm_backend/routes/absentReviewRoutes.js:133-149`). The same endpoint defines pending as `pending`, `none`, or `null` (`crm_backend/routes/absentReviewRoutes.js:151-154`) and then applies the rolling lower bound (`crm_backend/routes/absentReviewRoutes.js:164-165`). This is **confirmed**: after a missed cron lasting beyond the review window, an expired `none/null` absence fails the update and is excluded from the response while its leave type, review status, and multiplier remain unresolved. Use the same unresolved-status set for catch-up, listing, and cron settlement.

## Face punch-out does not record the verified source

Punch-in now stores `source: "face"` when `faceVerified === true` and `source: "manual"` otherwise (`crm_backend/routes/attendanceRoutes.js:133-138`). Punch-out still stores `source: "web"` regardless of the same request flag (`crm_backend/routes/attendanceRoutes.js:201-206`). This is **confirmed** for every Face Out and manual Punch Out through these routes: the source disagrees with the verification flag and the new punch-in contract. Apply the same strict boolean and source mapping to the out leg.

## Automatic detection can recreate the callback timer after close

Unmount cleanup clears `successTimer.current`, but automatic recognition awaits `detectSingleFace` while close remains enabled because auto scans do not set loading (`src/Components/FaceRecognition.jsx:231-246`). If the dialog closes during that await, cleanup runs before a timer exists; the matched branch then assigns a fresh timer and calls `onFaceMatched` 1.2 seconds later (`src/Components/FaceRecognition.jsx:289-306`). This is **confirmed** from the async ordering. Track mounted/cancelled state and re-check it immediately after detection and before scheduling or invoking the callback.

## Refreshed action selection still has a write race

The page refreshes today’s sessions, computes `expectedAction`, then sends a separate punch request (`src/HRMS/AttendancePage.jsx:312-329`). This is **likely** to race when a biometric or second web client writes after the GET but before or concurrently with the POST; the route reads, validates, mutates, and saves rather than claiming the transition atomically. Overlapping reads can both accept the same transition and later overwrite or duplicate session state. Move expected-state validation into an atomic backend mutation or send an attendance version/expected action and reject stale versions.

## Coverage stops at pure cutoff calculations

The simulation confirms the inclusive IST boundary, month rollover, and displayed deadline. The coverage gap is **confirmed** from the scoped changes: there is no route-level test for `none/null` catch-up, multiplier persistence, action cutoff parity, multi-session face transitions, an intervening update, or close-during-detection cancellation. Add targeted backend route tests and a fake-timer face component test.
