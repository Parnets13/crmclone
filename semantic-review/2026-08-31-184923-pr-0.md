# Confirmed discount ownership across Sales Orders and linked invoices

The change moves current-policy Sales Orders to Direct + Dealer Extra execution, keeps level discounts invoice-owned, and enforces each invoice actor’s live User Management assignments and policy caps. The main canonicalizers preserve promise shortfalls as guidance and replay persisted stages for legacy amount edits. Three defects remain in rollout and the Sales Executive entry path. Watch for: **confirmed (medium)** existing Super Admin workflows can lose every level after deployment; **confirmed (medium)** valid mapping-defined levels such as Silver/Gold/Platinum cannot be assigned to any role; **confirmed (medium)** reference-only level mappings can block Sales Executive requests before a Sales Order exists.

**Verdict**: NEEDS_CHANGES

## High-level view

Current web Sales Order creation and repricing build executable stages from Direct and Dealer Extra only. Level definitions remain reference data, promise metadata only computes guidance, and edits without explicit repricing preserve persisted financial stages.

Linked Dealer Invoices reconstruct source-owned Direct, Dealer Extra, GST, and promise while accepting invoice-owned levels. The server resolves the current actor for create, edit, and approval, then enforces per-level maxima, the combined level cap, and the master cap.

The permission rollout changes Super Admin from an implicit allow-list to a persisted assignment without migrating existing users. That assignment accepts only ten hard-coded names although discount mappings accept arbitrary names and the mapping model itself creates Silver, Gold, and Platinum.

The Sales Executive request path requires a combined level cap whenever a mapping supports levels and a master cap whenever any mapping exists, rather than only when corresponding executable stages are present.

<summary>Issues (3)</summary>

1. **Super Admin permission migration — confirmed (medium)** — Existing Super Admins can move from implicit full level access to an empty persisted assignment, blocking level selection and approval replay. Backfill explicit assignments before enabling the no-bypass semantics.
2. **Unassignable mapping level names — confirmed (medium)** — Discount mappings can define names that the User schema and User Management UI reject, so the authoritative invoice permission check makes those valid configured levels unusable. Use one canonical level-name source and migrate only names the product intentionally replaces.
3. **Reference-only cap gate — confirmed (medium)** — Sales Executive preview/request endpoints require master and combined caps even when no corresponding discount stage executes. Gate master caps on positive stages and combined caps on positive level stages.

## Persisted assignments revoke existing Super Admin levels at rollout

This is **confirmed (medium)** in `src/Sales&Purchase/DealerInvoice.jsx:365`, `src/Components/UserManagement.jsx:1194-1228`, and `crm_backend/controllers/dealerInvoiceController.js:214-230`. Before this change, Dealer Invoice treated every Super Admin as having the frontend’s full level list; the new frontend reads only `user.allowedDiscountLevels`, while backend canonicalization loads the persisted array and enables permission enforcement for every role.

Existing Super Admin documents were created while User Management hid this field, so an unset or empty array now means no level permission. No migration appears in the diff. Approval replay also uses the approver’s live array, so existing linked drafts with selected levels can become unapprovable. Backfill explicit assignments before deployment while retaining the intended no-bypass rule afterward.

## Mapping-defined level names exceed the User assignment namespace

This is **confirmed (medium)** in `crm_backend/models/DiscountMapping.js:4-8`, `crm_backend/models/DiscountMapping.js:483-500`, `crm_backend/models/User.js:124-137`, and `src/Components/UserManagement.jsx:1205-1227`. Discount mappings accept any trimmed `levelName`, and the model’s missing-level repair creates `Silver`, `Gold`, and `Platinum`. User documents and the assignment UI permit only the ten names from Loyalty Discount through Others.

Because the invoice canonicalizer now makes `allowedDiscountLevels` authoritative, any configured name outside that fixed enum cannot be assigned to any user and is rejected as `DISCOUNT_LEVEL_NOT_ALLOWED`. Populate assignments from the canonical mapping-level namespace and align or remove the conflicting User enum.

## Sales Executive requests demand caps for non-executing level references

This is **confirmed (medium)** in `crm_backend/SalesExecutiveAppBackend/controllers/orderRequestController.js:70-132` and `crm_backend/SalesExecutiveAppBackend/controllers/salesOrderController.js:909-972`. Both paths add level stages only for positive submitted rates, but require `masterDiscountCap` for every resolved mapping and `combinedLevelDiscountCap` for every mapping whose type supports levels.

A `both` mapping with Direct and no selected level is rejected only because the combined cap is absent. A level-only mapping with no selected level, Direct, or Dealer Extra is rejected for both missing caps despite executing no discount. Gate the master requirement on any positive stage and the combined requirement on a positive level stage, matching the web Sales Order and invoice canonicalizers.
