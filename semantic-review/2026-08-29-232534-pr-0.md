## Canonical replay remains valid after invoice state changes

The fingerprint includes invoice identity, normalized amount, method, type, optional date, remarks, and the active method-specific fields. Dealer, source, status, audit identity, invoice snapshots, and approval fields come from authenticated or database state rather than client-controlled replay input.

Replay lookup runs before invoice loading. Authenticated App requests use the server-resolved dealer plus App source and key; Web requests use invoice plus Web source and key before deriving the dealer. The dealer/source/key unique index and post-invoice lookup prevent reuse against another invoice or origin. Exact committed requests therefore replay after an invoice becomes draft or deleted, changed payloads return 409, and missing fingerprints fail closed.

## Payment-number collision exhaustion

`runPaymentTransaction` opens a new session after each recognized `paymentNumber` duplicate, allowing number generation to see the newly committed sequence. Exhaustion produces a status-bearing 409; idempotency-key duplicates instead re-read the committed payment and either replay it or return a payload conflict.

## Paise balances with persisted-value conflict guards

Rows must map exactly to integer paise. Voucher and invoice totals, paid amounts, row totals, and resulting balances are derived from those integers, so `0.10 + 0.20` is accepted against `0.30` and stores `0.3` allocated with `0` unallocated.

Expected-value filters use the voucher and invoice values read by the transaction rather than rounded replacements. Legacy zero balances allow missing or null storage; any concurrent balance change fails the matched-count checks and rolls back.

## Whole-plan auto-allocation rollback

Every voucher group invokes the canonical allocator with the same outer session. Later groups see earlier writes from that transaction, numbering uses the session, and any stale state or collision aborts all groups. Allocation-number retries rerun the complete plan.

## Missing financial concurrency tests

This package has no test script or focused payment/allocation tests. This is **confirmed (medium, non-blocking)**: changed modules pass `node --check`, and a direct arithmetic smoke check produced 10 + 20 = 30 paise against 30 paise, but the database retry and rollback paths remain unautomated.
