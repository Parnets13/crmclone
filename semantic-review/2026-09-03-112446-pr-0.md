# Delayed biometric reconciliation safeguards

Delayed biometric processing now requires a completed session before changing a closed day’s attendance decision. Completed pairs can restore machine-generated `auto_paid` leave only when no approved leave overlaps the IST day, while planned leave and explicit human decisions remain protected. Unmapped cards use a bounded retry pool, and the repair command scopes requeueing and processing to one validated IST date. Sync state now selects the greatest stored `sourceId` independently of the latest punch timestamp.

Watch for: No concrete regressions remain in the eight requested behaviors. The repair scripts were syntax-checked and exercised with an impossible date; persistence transitions were verified by tracing the changed paths, without treating the requested absence of new tests as a failure.

**Result**: PASS

**Verdict**: APPROVED

## High-level view

A closed historical day with no completed biometric pair writes session evidence without running Attendance status derivation. Leave rows return earlier, and Absent rows—including human-reviewed unpaid rows—retain their status and review metadata.

A completed pair releases only `Leave/auto_paid` after an approved-Leave overlap check. Explicit paid and unpaid decisions remain untouched, while automatic leave/review fields are reset before deriving Present or Late.

New pending punches and unmapped retries are queried independently. The primary queue keeps its full batch capacity while a bounded oldest-attempt retry pool remains replayable after card mappings change.

The repair command validates calendar components, applies one IST half-open range throughout, disables general retries, and fails if target-day punches remain unprocessed. Sync state separately finds maximum `sourceId` and latest `punchAt`.

## Completed-session gating preserves closed-day decisions

`hasCompletedBiometricSession` is computed before existing Attendance decisions are evaluated (`crm_backend/utils/biometricAttendance.js:214-217`). Leave without a completed pair exits unchanged. Every other closed historical day without a completed pair uses `Attendance.updateOne` to merge sessions without invoking status derivation (`crm_backend/utils/biometricAttendance.js:272-289`), so one delayed punch cannot promote Absent to Present/Late or reverse a manually reviewed unpaid row.

Only `Leave/auto_paid` with a completed pair proceeds toward restoration (`crm_backend/utils/biometricAttendance.js:223-242`). An inclusive overlap query protects approved Leave, every other Leave state returns unchanged, and completed pairs on `Absent/unexcused` rows with a human `reviewedBy` identity are protected (`crm_backend/utils/biometricAttendance.js:246-254`). Automatic expired unpaid rows remain distinguishable by `reviewedBy: null` and can follow completed machine evidence.

## Automatic absence metadata is removed before re-derivation

Eligible restoration resets status to Absent as the derivation baseline, clears `leaveType`, `reviewStatus`, `reviewReason`, `reviewedBy`, and `reviewedAt`, and restores the deduction multiplier to one (`crm_backend/utils/biometricAttendance.js:111-122`). The completed sessions then derive Present or Late without contradictory automatic leave or review metadata.

## Rotating unmapped retries cannot consume the main queue

The worker independently selects up to `batchLimit` new rows and up to `mappingRetryLimit` rows marked `processed: true, unmapped: true` (`crm_backend/utils/biometricAttendance.js:137-154`). Unresolved cards receive a refreshed `lastMappingAttemptAt`, keeping retries rotating while preserving the full primary batch for newer mapped punches.

## IST-day repair is scoped and self-checking

Both scripts round-trip numeric calendar components through `Date.UTC`, rejecting normalized dates before database access (`crm_backend/scripts/reconcileDelayedBiometricDay.mjs:10-29`, `crm_backend/scripts/inspectDelayedBiometricDay.mjs:12-31`). Direct execution confirmed that both reject `2026-02-30` with `Invalid calendar date`.

The repair uses the same `[IST midnight, next IST midnight)` range for counts, requeueing, processing, and post-run checks. `mappingRetryLimit: 0` excludes unrelated retry rows, the scoped batch exceeds the pre-read target count, and any target punch left `processed: false` raises an error (`crm_backend/scripts/reconcileDelayedBiometricDay.mjs:32-99`). Unmapped target rows are reported separately and retain their retry state.

## Source resume position is independent of punch chronology

`getSyncState` queries the highest non-null `sourceId` with a descending source sort and separately queries latest punch time (`crm_backend/controllers/biometricController.js:131-145`). Delayed or backdated punches therefore cannot move the Access-agent resume position backward.
