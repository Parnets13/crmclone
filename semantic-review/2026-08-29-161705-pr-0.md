# Centralized Sales Order maintenance and deferred sales-page loading

The performance changes remove duplicate browser work, defer heavy invoice/order form data, batch invoice payment enrichment, and move Sales Order expiry into a multi-company backend cron. Payment response fields and multiple allocation entries are preserved, independent data loads remain independent, and the expiry update is atomically guarded. The Sales Order list still lacks current-request ownership, its advanced Apply action duplicates the effect-owned fetch, and the active server picker remains disabled when the unrelated global product preload is empty. The new expiry schedule is data-idempotent but is registered once per cluster worker rather than once per deployment.

Watch for: **confirmed (high)** stale Sales Order list responses can replace newer filter/page results; **confirmed (medium)** Apply Filters issues a redundant list request; **confirmed (medium)** a failed/empty global product preload prevents the server-paginated dealer picker from opening; **confirmed (medium)** clustered deployments schedule the new global expiry scan in every worker; **confirmed (medium)** no automated regression coverage exercises the new batching, request ownership, or cron concurrency behavior.

**Verdict**: NEEDS_CHANGES

## High-level view

Dealer Invoice now performs one authenticated list load instead of overlapping initial effects, while products, taxonomy, warehouses, and live stock wait for the create flow. Dealer outstanding and delivered Sales Orders start together and write separate state, so the parallel branches have no shared result dependency.

Payment enrichment changes from two queries per invoice to two page-wide queries. The grouping retains the legacy response fields and includes each matching nested allocation, including multiple allocation documents or multiple matching entries for one invoice.

Sales Order list loading is owned by one effect, with page reset and search start debounce. That ownership stops at request start: older responses can still commit after newer ones, and the retained Apply button bypasses the single-owner model.

Existing order lines use persisted fields and new product choices come from the dealer-scoped server endpoint. The active picker still uses the global master-product array as its enablement condition, so failure of the lookup-only preload blocks the server path.

Products, stock, and pricing have no data dependency and can start in parallel. Browser expiry and stock mutation move to backend schedulers; the expiry write is conditional and preserves history, but scheduler registration is process-local rather than deployment-singleton.

4. **Per-worker expiry scheduling — confirmed (medium)** — Every cluster worker or service replica schedules the all-company scan. Run it in one scheduler process or under a distributed lease while retaining the conditional write.
5. **No performance-regression tests — confirmed (medium)** — No automated coverage verifies payment cardinality, out-of-order list completion, picker fallback, or concurrent expiry. Add focused controller, component, and cron tests.

<details><summary>Details</summary>

## Sales Order list starts are deduplicated, but responses are not ordered

The new effect schedules `loadSalesOrders(currentPage)` after zero or 300 milliseconds and only clears the timer (`src/Sales&Purchase/SalesOrderDashboard.jsx:1146-1153`). Once `apiService.getSalesOrders` starts, `loadSalesOrders` has no abort signal, generation token, or query-key comparison before updating orders and pagination (`src/Sales&Purchase/SalesOrderDashboard.jsx:659-710`). This is **confirmed (high)**: an immediate status, dealer, or advanced-filter change can start request B while request A is in flight; if A completes last, lines 696-706 replace the current results and can reset `currentPage` to A's page. The search debounce prevents obsolete timers from starting but does not protect requests already in flight.

Track a monotonically increasing request generation or use `AbortController`, and only commit orders, pagination, errors, and `refreshing` for the latest generation. Route effect-driven loads and explicit post-mutation refreshes through the same owner.

## Advanced Apply bypasses the effect-owned fetch

Every advanced filter is now a dependency of `loadSalesOrders` and the page-reset effect (`src/Sales&Purchase/SalesOrderDashboard.jsx:718-720`, `1316-1323`), so changing an advanced control already schedules its query. Apply Filters still calls `loadSalesOrders(1)` directly after setting page one (`src/Sales&Purchase/SalesOrderDashboard.jsx:5303-5307`). This is **confirmed (medium)**: on page one it repeats the request already issued by the filter change; off page one it can overlap the page-reset/effect request.

Remove the direct call and make Apply only commit draft filter state, or remove Apply and keep the controls live. Pagination and page-size handlers already use the required state-only pattern at lines 1351-1360.

## Global master-product failure disables the dealer-scoped picker

Removing the 100000-row dealer preload is compatible with persisted edit fields and the active `getDealerAccessibleProducts` path (`src/Sales&Purchase/SalesOrderDashboard.jsx:3031-3146`, `3681-3703`). Dealer selection now assigns `availableProducts` from the global 10000-row master request (`src/Sales&Purchase/SalesOrderDashboard.jsx:1694-1699`), while Browse & Add Products is disabled whenever that array is empty (`src/Sales&Purchase/SalesOrderDashboard.jsx:5998-6014`). This is **confirmed (medium)**: a failed or empty global request leaves the button disabled, so `fetchModalProducts` never runs even when the dealer endpoint is healthy and has products.

Enable the picker from dealer selection plus `modalOpening`, not `availableProducts.length`. Build active filter options from loaded dealer pages or dealer-scoped facets; retain the global array only as a best-effort lookup fallback for legacy persisted lines.

## Expiry writes are atomic, but scheduling is duplicated per worker

`runSalesOrderExpiration` repeats the expiry, status, and `isExpired` predicates in each `updateOne` (`crm_backend/cron/salesOrderExpiration.js:14-51`). Concurrent invocations therefore cannot append duplicate history: only the first matching update sets `Expired`, records `expiredAt`, and pushes the old endpoint's history shape.

The scheduler is registered inside the server's worker branch (`crm_backend/server.js:162-179`, `598-613`). This is **confirmed (medium)** when `USE_CLUSTER=true`: every CPU worker calls `startSalesOrderExpirationCron`, and multiple service replicas do the same, causing each process to scan all company databases every minute. The write predicate protects data but not duplicate reads, candidate materialization, logging, or bulk submissions.

Run the global job in a dedicated scheduler process, the cluster primary, or behind a database/Redis lease. Keep the conditional update as the final idempotency guard.

## Payment batching lacks cardinality and concurrency regression coverage

The page-wide PaymentAllocation grouping iterates every matching nested entry (`crm_backend/controllers/dealerInvoiceController.js:675-723`), and lines 733-735 always attach the legacy `paymentAllocations` and `oldPayments` arrays. Multiple allocation documents and multiple matching entries are retained with the old field names and fallbacks.

Neither package exposes a test script (`crm_backend/package.json:5-9`, `package.json:6-12`), and no scoped test files cover the changed behavior. This is a **confirmed (medium)** gap because the failure modes are timing- and cardinality-dependent. Add controller fixtures with multiple PaymentAllocation documents and multiple matching nested entries, component tests with out-of-order completion and page reset, and a cron test that invokes the runner concurrently and asserts one history entry per order.
