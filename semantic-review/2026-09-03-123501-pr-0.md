# Live dealer-state guards for Sales Order pricing

The change validates DealerInfoPanel responses against live dealer and modal-mode refs, preventing the original stale A response from writing after a switch to B and keeping edit snapshots out of add-mode repricing. Initial dealer-extra hydration, the three promise inputs, allowed-only reference potential, inverse cap allowance, `targetId`, and server-canonical actual totals remain intact. Dealer identity is still the only request token, so an older A request can become valid again after A→B→A and replace newer state for A.

Watch for: **confirmed** same-dealer request generations remain unordered, allowing an old complete-info response or credit-history completion to overwrite newer state after A→B→A or a same-dealer refresh/remount.

**Verdict**: NEEDS_CHANGES

## High-level view

The live refs close the direct A→B race: callbacks for a dealer different from the current selection return before writing payment state, repricing lines, or starting history work. **Confirmed:** they do not distinguish two requests for the same dealer, so returning to A makes every outstanding A request eligible again.

`modalTypeRef` is checked before scheduling and inside the functional form update. Once edit mode is established, a delayed add-mode callback for the same dealer cannot recalculate persisted edit lines.

Create-mode dealer extras cover both arrival orders: the response ref supplies products selected later, while already-selected products are recalculated on arrival. Promise percentage, promised unit price, and additional sequential stage remain inverse views of one persisted promise; only allowed levels feed reference potential, all levels remain visible as Allowed or View only, and cap allowance uses the inverse sequential stage on remaining value.

The complete-info API returns `targetId` for hierarchy matching. Actual direct/dealer-extra stages and totals remain server-resolved: create derives totals from canonical lines, while update discards client totals and replays persisted policy or canonicalizes explicit repricing.

## Dealer identity becomes valid again after A→B→A

`DealerInfoPanel` starts uncancelled requests on dealer changes and retries, while the parent checks only `status.dealerInfo.dealerId` against `activeDealerIdRef.current`. This is **confirmed** insufficient for request ordering: if A1 remains pending while the user selects B and then A, A1 passes the live-ID check and can replace newer A2 payment state; in add mode it can also recalculate current A lines using A1's extra-discount snapshot.

Credit-history requests have the same **confirmed** generation hole. A history request started by A1 checks only that A is active when it completes, so it can overwrite history loaded or cleared by a newer A callback. Add a monotonically increasing request token or cancellation signal, carry the accepted generation into history loading, and require both dealer ID and generation before every write.

</details>
