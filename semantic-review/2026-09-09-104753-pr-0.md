# Safety-gated Shree Jain transaction reset

The reset is hard-locked to `shree-jain-impex`, defaults to dry-run, and applies the approved transaction deletion and opening/accounting preservation boundary. The dynamic journal predicate now combines approved reference types with IDs from every voucher scheduled for deletion, and its retained complement is fingerprinted alongside retained accounting records, legacy opening adjustments, and non-GRN counters. Live apply rechecks deletion plans inside the transaction, but the manifest does not fingerprint the pre-reset values of fields it intentionally overwrites. No transaction-backed integration test exercises that destructive boundary.

Watch for: **confirmed (P1)** the reviewed manifest remains valid when dealer transactional fields, opening running balances, opening stock balances, or cash/bank balances change before apply; **confirmed (P2)** only static syntax/diff validation covers the destructive transaction and rollback behavior.

**Verdict**: NEEDS_CHANGES

## High-level view

Journal deletion is provenance-based: non-opening journals outside the approved reference types and voucher IDs form an exact retained complement, preserving expense, TDS, depreciation, and unrelated manual journals while removing voucher-origin journals.

The preservation snapshot includes exact hashes for retained journals, expenses, TDS entries, financial-year closings, year-end checklists, completed legacy opening adjustments, and retained non-GRN counters. Bank reconciliations are part of the full-delete plan with the vouchers they reference.

The stale-plan gate is incomplete for update operations. Fields excluded from preservation hashes because they are recomputed are represented only by collection counts, so their values can drift after dry-run without changing the manifest or failing in-transaction preflight.

There is no isolated replica-set fixture covering manifest drift, journal partitioning, rollback, or exact preservation across commit.

## Mutation targets are outside the reviewed manifest

This is **confirmed (P1)** in `scripts/resetShreeJainTransactions.mjs:283-297, 539-550, 663-665, 919-985`. Dealer transactional fields and cash/bank current balances are removed from protected-document hashes, while opening dealer/supplier ledger hashes omit `runningBalance` and the opening-stock hash omits `balance`. The manifest records only counts for dealer, bank, and cash update targets, with no separate full pre-mutation fingerprints for the omitted ledger and stock fields.

A dealer's `advanceBalance`/`advancePayments`, an opening row's `runningBalance` or `balance`, or an account's `currentBalance` can change after dry-run without altering the fingerprint supplied to `--apply`. `assertPlanUnchangedInTransaction` compares the same omission-based snapshot (`scripts/resetShreeJainTransactions.mjs:775-822`), so it accepts the stale plan and overwrites those newer values. Post-write checks prove the normalized result, not that the destroyed values matched the reviewed dry run.

Keep an exact before-state fingerprint that includes every field alongside the omission-based expected-after hash. Recompute the exact hash inside the transaction before the first write.

## Destructive transaction behavior has no executable fixture

This is **confirmed (P2)** from the working tree: the reset script is the only source addition and no test accompanies it. `node --check scripts/resetShreeJainTransactions.mjs` and `git diff --check --no-index` pass, but neither executes MongoDB snapshot transactions, stale-manifest refusal, rollback after pre-commit failure, or the journal/opening-data partition.

Add an isolated replica-set fixture that seeds approved transaction and retained accounting variants, changes one fingerprinted field between dry-run and apply, forces a pre-commit verification failure, and verifies rollback and the successful preserve/delete boundary.
