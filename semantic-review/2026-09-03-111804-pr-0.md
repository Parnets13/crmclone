# Delayed biometric leave and absence reconciliation

Delayed source punches are bucketed by their stored timestamp into IST attendance days, and completed pairs can now restore system-generated auto-paid leave while preserving approved leave and explicit human decisions. The sync-state endpoint independently reports the maximum Access `sourceId`, and unmapped rows remain pending for later card assignment. Automatic decision metadata is cleared before a completed pair derives its new state, but open punches still pass through derivation that promotes them to attendance. The one-day replay script also invokes an unscoped global queue, so it can mutate other dates or miss the requested date.

Watch for: **confirmed** a single delayed punch converts Absent and human-reviewed unpaid rows to Present/Late; **confirmed** retryable unmapped rows can permanently block the oldest-first queue; **confirmed** the day reconciliation script processes unrelated pending dates and accepts impossible calendar dates that normalize to a different day; **confirmed** these state transitions have no automated regression coverage.

**Verdict**: NEEDS_CHANGES

## High-level view

The punch’s `punchAt` value, rather than upload time, selects the IST day. The Access agent sends the source wall clock with `+05:30`, ingestion stores that instant, and reconciliation derives the day from it, so next-day upload does not move the attendance date.

A completed biometric pair can release `Leave/auto_paid` only after an approved-Leave overlap check. Other Leave rows and manually reviewed unpaid Absences are intended to remain protected, while automatic decision metadata is reset before Attendance derives Present or Late.

**Confirmed:** the completed-pair gate is not applied to the subsequent save. An open biometric session on an Absent row reaches the Attendance hook and promotes the row to Present/Late, including a manually reviewed unpaid decision.

**Confirmed:** keeping unmapped punches unprocessed provides replayability, but the oldest fixed-size selection allows a sufficiently large unmapped backlog to block every newer mapped punch.

**Confirmed:** the replay command initially requeues only the requested IST day, but its processing call is global and its date parser validates syntax rather than the calendar day.

<details><summary>Details</summary>

## Open delayed sessions bypass the no-punch-out and human-review protections

This is **confirmed** in `crm_backend/utils/biometricAttendance.js:188-242`. `hasCompletedBiometricSession` gates reversal of `Leave/auto_paid` and protection of a human `Absent/unexcused` row, but an Absent row with one punch falls through, receives the open biometric session, and is saved. The unchanged Attendance hook derives status from the first in-time even when no completed session exists (`crm_backend/models/Attendance.js:91-135`), changing the row to Present or Late.

The finalizer revisits only yesterday at 00:20 IST (`crm_backend/cron/hrmsCron.js:364-365`), so a punch uploaded after that pass remains Present/Late. On a manually reviewed unpaid row, status changes while `reviewStatus: unexcused`, `reviewedBy`, and deduction metadata remain attached, producing a contradictory record. Open delayed sessions must preserve Leave/Absent and explicit review decisions; only a completed pair should enter restoration.

## Retryable unmapped punches can monopolize biometric processing

This is **confirmed** in `crm_backend/utils/biometricAttendance.js:129-158,251-264`. The worker sorts all `processed: false` rows by `punchAt`, limits the result to 5,000 by default, and leaves every unresolved card unprocessed. Once the oldest 5,000 pending rows are unmapped, every five-minute run selects the same rows and leaves all newer mapped punches untouched.

Retryability needs a queue policy that cannot starve valid work, such as resolving before applying the processing limit, recording retry state/backoff, or separately replaying unmapped cards when a mapping changes.

## Day replay delegates to a global pending queue

This is **confirmed** in `crm_backend/scripts/reconcileDelayedBiometricDay.mjs:49-64`. The script requeues punches inside the selected IST range, then calls `processBiometricPunches`, whose query has no day filter. Older pending punches up to `Math.max(5000, punchCount + 100)` are processed too, so a one-day command can rewrite biometric sessions and attendance on unrelated dates.

An older backlog can also consume the batch before a requeued target punch is reached. The script still exits successfully; `remainingAutoPaid` is informational and does not prove every requested punch was evaluated. The processor needs an explicit day or punch-ID scope plus a failing postcondition when target rows remain unprocessed.

## Impossible dates can target a different real day

This is **confirmed** in both `parseIstDay` implementations (`crm_backend/scripts/reconcileDelayedBiometricDay.mjs:11-17`, `crm_backend/scripts/inspectDelayedBiometricDay.mjs:13-19`). The regex checks shape and `getTime()` checks parseability, but JavaScript normalizes `2026-02-30T00:00:00+05:30` to 2026-03-02 IST. With `--apply`, the script logs the impossible requested date while requeueing the normalized real day. Round-trip the parsed IST year, month, and day before allowing apply.

## Required reconciliation states lack regression coverage

This is **confirmed** by the scoped repository search: no automated test or simulation invokes `processBiometricPunches` or the replay command. Syntax checks pass but cannot validate the required persistence transitions.

Not tested: a delayed single punch against automatic and human-reviewed Absence; a completed pair against `auto_paid` with and without approved Leave overlap; metadata clearing; a batch-sized unmapped backlog; replay with unrelated older pending rows; invalid dates; source-day bucketing; out-of-order `punchAt` versus `sourceId`.
