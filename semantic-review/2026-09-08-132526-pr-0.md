# Read-path optimization for purchase orders, GRNs, and stock

This batch removes duplicate frontend work, rejects stale list responses, serializes stock polling, pushes GRN supplier filtering into the database query, and parallelizes independent backend reads. The PO lifecycle, extension, detail, and PDF paths are not modified; GRN claims and stock mutation logic are also outside the changed backend regions. The compact PO product preload retains the persisted Product fields used by the picker and still receives computed `stockInfo`. **Watch for:** No concrete behavioral regression, race-condition regression, or invariant violation was found; no fix is required before completion.

**Verdict**: APPROVED

## High-level view

Purchase-order count/page reads now begin together. The frontend removes one duplicate initial list request and opts into the existing compact product response; lifecycle transitions, effective-expiration checks, extension refresh, detail loading, and PDF data remain outside the changes.

GRN approved-PO lookup now applies supplier id in MongoDB before sorting and the 20-row limit. Approved status, effective future expiry, `convertedToGRNId`, and the union of legacy `poId`/`poIds` usage remain in the eligibility query; frontend request generations reject older supplier and list responses.

Stock polling now waits for a request to settle before scheduling the next poll and invalidates stock and advisory sales responses on filter changes or unmount. The backend only parallelizes stock-history page/count reads; StockMovement direction, damage/block behavior, product+warehouse scoping, movement order, and live order enrichment are unchanged.

## GRN supplier pushdown preserves eligibility and claims

The supplier condition is composed into the approved-PO query before `.sort(...).limit(20)`, correcting client-side-after-limit behavior without broadening eligibility. Search is an additional `$or` condition under that supplier, and used-PO exclusion still combines distinct values from primary `poId` and legacy/multi-PO `poIds`. No changed line touches GRN create/update/inspection transactions, serial draft resolution, source-PO mutation, or stock movement creation.

Each approved-PO effect generation invalidates its predecessor, and each GRN list generation checks its id before writing rows, pagination, errors, or loading completion. Debouncing applies only to free-text list search; tab, date, and page dependencies remain immediate. Mutation-triggered `loadGRNs()` calls create a newer generation, preventing a pre-mutation list response from overwriting the refresh.

## PO parallel reads leave lifecycle and response data intact

Search and non-search branches retain their filters, sort, pagination, and population fields. Count and page remain separate MongoDB operations as before, so parallel execution changes latency rather than adding or removing a cross-query snapshot guarantee. No lifecycle write, effective-expiry predicate, extension handler, detail endpoint, or PDF field selection changes.

The removed mount call duplicated the filter-driven effect’s initial list request. The compact preload projects product identity, hierarchy, GST, MRP/total/rate data, units, status, and minimum stock; the existing product controller appends `stockInfo`.

## Stock polling serialization leaves stock authority unchanged

Settle-then-timeout polling prevents overlapping periodic stock requests. Cleanup cancels pending recursion and advances request generations so in-flight responses cannot update a new filter/page or an unmounted component. Sales analytics has a separate generation, preventing an older page’s advisory quantities from replacing the latest page’s map.

Stock history retains `{ productId, warehouseId? }`, descending `{ date, createdAt }` order, page boundaries, movement population, and live sales-order enrichment. Only page/count reads are parallelized and diagnostic full-ledger work is removed. Signed IN/OUT authority, blocked/damaged quantities, product+warehouse stock keys, FIFO mutation ordering, reservations, and order/invoice validation are not changed.
