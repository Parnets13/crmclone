# Super Admin authorization for one-time above-MRP invoice pricing

The change adds an invoice-owned post-discount increase whose above-MRP use is authorized from the authenticated database user’s normalized `super_admin` role. Server canonicalization replaces client totals, permits an uncapped non-negative percentage only behind the explicit Boolean override, and replays linked Sales Order drafts from authoritative pricing inputs. Active overrides can still be removed or have protected inputs changed by a non-Super Admin through unmatched or rebalanced lines. The MRP comparison also leaves a one-cent unflagged gap.

Watch for: **confirmed (P1)** unmatched existing override lines can be deleted or product-replaced without reaching the authorization check; **confirmed (P1)** protected quantity/MRP inputs can be rebalanced while preserving aggregate gross and bypass the non-Super Admin guard; **confirmed (P1)** normal lines may finish ₹0.01 above MRP without an override; **confirmed (P2)** gross-only changes can preserve stale override audit attribution; **confirmed (P2)** the frontend leaves protected reason/removal state editable for non-Super Admin users; **confirmed (P2)** no automated coverage exercises the new pricing security boundary.

**Verdict**: NEEDS_CHANGES

## High-level view

`canonicalizeInvoiceItems` is the shared create/update authority and loads the actor’s role from the tenant database. Linked Sales Order approval replays persisted lines through the same canonicalizer, allowing unchanged matched overrides to retain their audit while replacing submitted totals.

The authorization is scoped only to submitted lines that match an existing item. An omitted line or a stable ID paired with a replacement product becomes unmatched, allowing a non-Super Admin to remove an active standalone override before approval.

Protected-input detection compares only the derived pre-increase amount and aggregate gross. Quantity and MRP can move in opposite directions without being recognized as protected mutations, while the audit-preservation predicate independently omits gross changes.

All three server layers and the frontend use a `MRP + ₹0.01` threshold. Because final amounts are already rounded to cents, this admits exactly one cent above MRP as an ordinary line and clears the override flag.

The UI requires a reason, shows an explicit confirmation before an above-MRP submit, and keeps the audit annotation in internal invoice detail rather than customer print output. It does not lock all protected fields for a non-Super Admin editing a persisted override.

## Active override removal bypasses matched-line authorization

This is **confirmed (P1)**. `findExistingInvoiceItem` returns `null` when a submitted stable line ID is paired with a different product, and `canonicalizeInvoiceItems` only tracks duplicate identities among submitted, successfully matched items (`crm_backend/controllers/dealerInvoiceController.js:59-83`, `409-420`). There is no post-pass requiring every existing active override to remain matched. `updateDealerInvoice` then replaces the entire items array with the canonicalized submission (`crm_backend/controllers/dealerInvoiceController.js:2640-2653`).

A non-Super Admin can omit an active override line or replace its product in a standalone draft; no authorization check sees the old override, and standalone approval does not replay items. The remove button exposes the same path for standalone lines regardless of override ownership (`../jainimpex-frontend-all/src/Sales&Purchase/DealerInvoice.jsx:4044`). Reject any non-Super Admin update when an existing effective override identity is absent, changes product, or is otherwise unmatched.

## Aggregate comparisons do not protect base pricing inputs

This is **confirmed (P1)**. The non-Super Admin guard derives `priceBeforeIncreaseIsUnchanged` and `grossAmountIsUnchanged`, then treats the override inputs as unchanged when those aggregate values remain within tolerance (`crm_backend/controllers/dealerInvoiceController.js:131-151`). It never compares quantity, MRP, reference unit price, GST, or discount-driving stages themselves.

Standalone pricing uses submitted MRP as its base (`crm_backend/controllers/dealerInvoiceController.js:229-235`). A client can change quantity from 1 to 2 and MRP from ₹100 to ₹50, preserve gross and pre-increase totals, and pass the guard. Compare canonical protected fields individually against the persisted line; aggregate equality is an additional invariant, not the identity of the inputs.

## One-cent amount above MRP remains an ordinary line

This is **confirmed (P1)**. The shared helper rejects only when `finalAmount > roundedMaximum + 0.01` (`crm_backend/utils/sequentialDiscountPolicy.js:326`), and both controller and model classify an override only above the same `roundedGross + 0.01` boundary (`crm_backend/controllers/dealerInvoiceController.js:164-167`, `crm_backend/models/DealerInvoice.js:465-481`). A smoke call with a ₹100 base and 0.01% increase returned ₹100.01 without error; 0.02% rejected.

Both values are already cent-rounded, so compare them directly with no extra tolerance. Align the frontend boundary so confirmation and warning state match the server (`../jainimpex-frontend-all/src/Sales&Purchase/DealerInvoice.jsx:224-230`).

## Gross changes can retain the previous Super Admin audit

This is **confirmed (P2)**. `grossAmountIsUnchanged` participates in non-Super Admin authorization but is absent from `auditIsUnchanged` (`crm_backend/controllers/dealerInvoiceController.js:138-145`, `194-207`). If a Super Admin changes gross/base inputs while keeping the rounded pre-increase amount and effective override state stable, the old actor and timestamp survive.

Use one canonical protected-input comparison for both authorization and audit refresh. This prevents attribution from drifting as pricing fields evolve.

## Non-Super Admin edit state is only partially locked

This is **confirmed (P2)**. The active-override percentage is disabled for a non-Super Admin (`../jainimpex-frontend-all/src/Sales&Purchase/DealerInvoice.jsx:4093-4102`), but the reason remains editable (`4116-4127`) and standalone removal remains enabled (`4044`). Base inputs and discount controls also remain interactive, so a normal edit can build state the server rejects; removal currently reaches the authorization bypass above.

Lock removal, reason, and every override-protected pricing control while a persisted effective override is active. The server must remain authoritative, but the client should not present forbidden mutations as valid edits.

## Security-critical pricing paths have no regression suite

This is **confirmed (P2)**. No test file references `calculateOneTimeInvoicePriceIncrease`, `MRP_OVERRIDE_FORBIDDEN`, or `oneTimePriceIncreaseAboveMrpOverride`; the backend package defines no test script. Scoped validation was limited to syntax, a direct boundary/overflow smoke call, and a frontend build that timed out during dependency transformation.

Add focused coverage for create/update authorization, omitted or replaced duplicate lines, linked-SO replay under a non-Super Admin approver, standalone approval, exact-MRP and one-cent-over boundaries, malformed Boolean values, overflow, reason enforcement, and audit preservation/refresh. Exercise model pre-save with the same boundaries so persistence cannot diverge from controller behavior.
