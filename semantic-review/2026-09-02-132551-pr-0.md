# Hardened Super Admin override for above-MRP Dealer Invoice lines

The fixes close the previously identified ways a non-Super Admin could remove or mutate an active above-MRP line, align server comparisons on the cent-rounded MRP boundary, and refresh override attribution whenever protected pricing changes. Create and update replace submitted monetary values with canonical calculations, while linked-Sales-Order approval replays persisted lines through the same authorization path. The focused regression review found no remaining blocking issue; automated coverage was intentionally not added at the user's request.

Watch for: no blocking Dealer Invoice above-MRP override concern remains at **confirmed** confidence; the only scope limitation is the explicitly requested absence of new automated tests.

**Verdict**: APPROVED

## High-level view

Existing lines are matched by stable identity and product, and every persisted active override must be accounted for after canonicalization. Omission, product replacement, duplicate identity reuse, and protected-field edits fail closed for a non-Super Admin while a Super Admin can disable or remove the override.

Authorization uses the tenant-database User record. Quantity, MRP, reference unit price, GST, pre-increase amount, gross, ordered stage fingerprint, percentage, reason, and effective override state form the protected comparison that also controls audit preservation.

The shared helper accepts any finite non-negative percentage when no maximum is supplied, rejects non-finite arithmetic, and rejects any cent-rounded final amount above the maximum when the override is off. Controller and model normalize the persisted Boolean to whether the line actually exceeds MRP.

Create and update canonicalize totals before persistence. Linked-SO approval replays the draft inside its transaction, and model pre-save recomputes line and invoice totals when items change; unchanged active overrides can be approved by a non-Super Admin without granting authority to alter them.

The frontend uses the same role normalization and makes active override percentage, reason, removal, and level-discount controls read-only for other users. Handler guards back up the disabled controls.

## Active override identity survives replacement and removal attempts

The previous omission/product-replacement bypass is **confirmed resolved**. A submitted identity only matches when its product also matches (`crm_backend/controllers/dealerInvoiceController.js:59-83`), successful matches are recorded once (`443-454`), and duplicate submitted identities are rejected (`387-399`). After canonicalization, every existing item with an effective override must be in the matched set; otherwise the database actor must normalize to `super_admin`, or the request fails with `MRP_OVERRIDE_FORBIDDEN` (`916-929`).

Update supplies persisted items as `existingItems` and the authenticated user as actor (`crm_backend/controllers/dealerInvoiceController.js:2701-2713`). Omission and replacement therefore fail for non-Super Admins, while the post-pass deliberately permits Super Admin removal.

## Protected pricing fingerprints atomic inputs and ordered stages

The inverse quantity/MRP bypass is **confirmed resolved**. Quantity, MRP per unit, reference unit price, and GST are compared individually (`crm_backend/controllers/dealerInvoiceController.js:138-153`), alongside pre-increase amount and cent-rounded gross (`130-157`). Opposing quantity and MRP changes cannot hide behind an unchanged aggregate.

Stages are serialized in order by key, kind, level name, and six-decimal rate (`158-166`), so reorder, identity, or rate changes fail the predicate even if a rounded payable amount is unchanged. Percentage, reason, protected pricing, and requested override state feed the non-Super Admin check (`125-185`); the derived effective flag is checked separately (`197-206`).

## Exact MRP boundary and effective flag normalization

The prior ₹0.01 gap is **confirmed resolved**. The helper rejects `finalAmount > round(maximumFinalAmount, 2)` without extra tolerance (`crm_backend/utils/sequentialDiscountPolicy.js:321-328`). Controller classification (`crm_backend/controllers/dealerInvoiceController.js:188-200`), model persistence (`crm_backend/models/DealerInvoice.js:447-467`), and frontend warning state (`../jainimpex-frontend-all/src/Sales&Purchase/DealerInvoice.jsx:222-230`) use the same cent-rounded boundary.

There is no fixed percentage ceiling: the schema has only a zero minimum (`crm_backend/models/DealerInvoice.js:154-157`), and the helper accepts finite non-negative values (`crm_backend/utils/sequentialDiscountPolicy.js:303-318`). Without an override, the exact MRP maximum applies. Non-Boolean override input is rejected (`crm_backend/controllers/dealerInvoiceController.js:106-117`), and overflow fails closed (`crm_backend/utils/sequentialDiscountPolicy.js:311-318`).

Requested `true` is normalized rather than blindly persisted. Controller and model retain it only for a positive increase above rounded gross (`crm_backend/controllers/dealerInvoiceController.js:197-200`; `crm_backend/models/DealerInvoice.js:465-481`); a zero increase clears flag and audit (`crm_backend/controllers/dealerInvoiceController.js:216-223`).

## Audit attribution follows protected mutations

The stale actor/time finding is **confirmed resolved**. `auditIsUnchanged` requires unchanged percentage, reason, the full protected-input predicate, and effective state (`crm_backend/controllers/dealerInvoiceController.js:226-243`). Quantity, MRP, unit price, GST, gross, pre-increase amount, or stage changes refresh actor and timestamp when a Super Admin makes them.

An unchanged replay retains existing audit fields. A Super Admin can disable an override with a non-exceeding percentage or zero; zero clears reason and audit, while unmatched line removal is allowed only when the live database role normalizes to `super_admin` (`crm_backend/controllers/dealerInvoiceController.js:921-929`).

## Create, update, and linked-SO replay share canonical authority

Create canonicalizes with the authenticated user and reduces all totals from canonical items (`crm_backend/controllers/dealerInvoiceController.js:1819-1839`). Update uses the same function with persisted comparison state (`2701-2713`). Model pre-save recalculates changed lines, normalizes the effective flag, and rebuilds invoice totals (`crm_backend/models/DealerInvoice.js:435-500`).

Linked-SO approval replays persisted submitted and existing representations through `canonicalizeInvoiceItems` inside the transaction (`crm_backend/controllers/dealerInvoiceController.js:2286-2319`). An unchanged override passes for a non-Super Admin because requested and effective state do not change; mutations still reach the role checks. Standalone approval accepts no item payload and uses the canonical draft.

Canonicalization loads role and discount permissions from the tenant User record (`crm_backend/controllers/dealerInvoiceController.js:419-435`) and normalizes role by trimming, lowercasing, and converting spaces/hyphens to underscores (`118-119`, `923-924`).

## Non-Super Admin controls mirror the server boundary

The frontend editability finding is **confirmed resolved**. Role normalization matches the backend (`../jainimpex-frontend-all/src/Sales&Purchase/DealerInvoice.jsx:607-609`). The central handler rejects active-override product, quantity, unit price, MRP, GST, percentage, flag, and reason changes (`1620-1635`); removal and discount handlers also return without mutation (`1760-1775`, `1990-2005`).

The rendered `overrideReadOnly` state (`3932-3935`) disables removal (`4074-4083`), percentage and reason (`4128-4163`), and level controls (`4520-4611`). “Clear all” still renders but routes through the guarded handler (`4691-4697`, `1771-1775`), so it cannot edit an active override.
