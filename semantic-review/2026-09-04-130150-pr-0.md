# Unified Sales Order stock lifecycle

This change makes aggregate `IN - OUT` movements the stock truth, starts every Sales Order as `Pending`, and turns stock arrival into FIFO readiness rather than automatic confirmation or reservation. Explicit confirmation owns reservation; delivery, cancellation, partial dispatch, invoice reversal, GRN receipt, adjustments, opening stock, and transfers feed the same ledger. Retry recovery and several concurrent mutation paths still violate that lifecycle. **Watch for:** **high, confirmed** confirmation retries blocked by their own reservation; **high, confirmed** FIFO refreshes overwriting concurrent Pending-order edits; **high, confirmed** Draft GRN races mutating or removing received GRNs; **high, confirmed** duplicate adjustment/transfer lines overdrawing stock; **high, confirmed** expiry racing confirmation and stranding reservations; **medium, confirmed** retried creates duplicating adjustments or transfers.

**Verdict**: NEEDS_CHANGES

## High-level view

Physical availability now comes from movement direction and quantity, while FIFO readiness decrements a shared product/warehouse pool. Confirmation rechecks aggregate availability under stock leases and emits per-line reservation identities.

Confirmation runs FIFO readiness before recognizing existing deterministic reservations. A crash after reservation insertion can make the still-Pending order fail its own readiness gate instead of healing the status write.

FIFO refresh bulk-writes complete `products` arrays from an unlocked snapshot. Concurrent Pending edits can be replaced by stale lines, not merely left with temporarily stale readiness metadata.

GRN inspection locks stock keys from a pre-transaction read, while Draft edit and delete use stale prechecks and unconditional final writes. An inspection commit can therefore be followed by an edit or deletion of the now-received GRN.

Adjustment and transfer availability is checked per request row, so duplicate rows can each pass against the same balance and cumulatively make stock negative. Their operation identities also change when the whole request is retried.

Expiry targets Pending orders but does not use the `SALES_ORDER:<id>` lease. It can race between reservation insertion and confirmation status persistence, producing terminal expiry state with reserved stock.

<summary>Issues (6)</summary>

1. **Confirmation retry self-blocks — high, confirmed** — Existing reservation OUT rows reduce the FIFO balance before retry recovery checks their operation keys. Recover or credit this order's reservations before applying the readiness gate.
2. **FIFO refresh overwrites Pending edits — high, confirmed** — Whole `products` arrays are written from stale snapshots without an order lease/version. Update only stock-owned line fields with revision checks, or lock and re-read each order.
3. **Received GRN can be edited or deleted — high, confirmed** — Draft checks and final writes are not atomic with inspection. Share a GRN lifecycle lease and make edit/delete predicates require the current Draft revision.
4. **Duplicate rows can overdraw stock — high, confirmed** — Adjustment and transfer rows validate independently but post cumulatively. Aggregate by source stock key or reject duplicates before availability checks.
5. **Expiry can strand reservations — high, confirmed** — Manual and scheduled expiry bypass the Sales Order lifecycle lease. Acquire the same per-order lease and condition confirmation's final status write on the locked Pending revision.
6. **Create retries duplicate stock mutations — medium, confirmed** — Adjustment and transfer operation keys derive from new server-generated ids on every request. Persist a client/request idempotency key and return the existing operation on retry.

## Existing reservations make confirmation retries fail FIFO readiness

This is a **high, confirmed** defect in `controllers/salesOrderController.js:1400-1409` and `1599-1604`. Confirmation calls `refreshAllPendingOrders` and rejects unless the order is `ready`; only later does it query `SO:<order>:RESERVE:<line>` and skip stock reserved by a previous attempt.

```text
stock = 10, Pending order requests 10
confirmation writes reservation OUT 10
process fails before SalesOrder.status is saved
retry refresh sees stock = 0
retry returns SALES_ORDER_NOT_FIFO_READY
```

The transition never reaches its deterministic recovery logic, including when only some lines were reserved. Move reservation recovery ahead of FIFO gating, or add this still-Pending order's verified reservations back to its FIFO allocation; then append only missing reservations before saving `Confirmed`.

## FIFO refresh can replace business edits with stale product arrays

This is a **high, confirmed** lost-update race in `services/stockArrivalService.js:46-130`. The service reads all Pending orders with `.lean()`, builds replacement arrays, then runs `$set: { products, ... }` with a filter that checks only `_id`, `status`, and `isExpired`.

An edit to quantity, warehouse, pricing snapshots, or line membership between the query and `bulkWrite` is overwritten. The status-only compare-and-set in `controllers/salesOrderController.js:2756-2762` cannot detect this because both operations leave the order Pending, and normal cron, arrival, creation, manual refresh, and confirmation paths invoke this writer. Persist only stock-owned line fields with line-id/revision predicates, or acquire `SALES_ORDER:<id>` leases and re-read before writing; rebuild on a revision miss.

## Draft-only GRN guards can become stale after inspection

This is a **high, confirmed** lifecycle defect in `controllers/grnController.js:743-797` and `809-843`, interacting with inspection at `355-368`. `updateGRN` checks Draft and later unconditionally calls `findByIdAndUpdate`, explicitly restoring `status = Draft`; `deleteGRN` checks Draft and later unconditionally calls `findByIdAndDelete`.

If inspection commits `Received` and receipt movements after either precheck, the stale update can alter posted lines or the stale delete can remove the received GRN while stock remains. Draft edits can also change items or warehouse after inspection chooses lease keys. Use a shared `GRN:<id>` lease for inspect/edit/delete, re-read after acquisition, and condition edit/delete on `_id`, `status: 'Draft'`, the invoice guard, and a revision; derive inspection stock keys from that locked revision.

## Duplicate adjustment and transfer rows can make stock negative

This is a **high, confirmed** accounting defect in `controllers/stockAdjustmentController.js:75-101,127-151` and `controllers/stockController.js:710-773`. With 10 units available, two REMOVE/transfer rows of 6 for one stock key each pass `10 >= 6`, after which `appendMovements` emits both OUT rows and leaves -2.

Leases serialize other requests but do not aggregate this request. Group quantities by source product/warehouse before validation and movement generation, or reject duplicate source keys.

## Expiry does not share the Sales Order lifecycle lease

This is a **high, confirmed** race across `controllers/salesOrderController.js:2079-2108,4183-4234,4651-4680` and `cron/salesOrderExpiration.js:65-106`. Status transitions hold `SALES_ORDER:<id>`, but manual expiry, controller auto-expiry, and cron expiry do not; the company cron lease excludes only another cron worker.

Expiry can mark the still-Pending order `Expired` after reservation writes but before confirmation persists `Confirmed`. If confirmation then stops, the terminal order retains reservations and cannot use the normal retry or cancellation transition. Process each expiry candidate under the per-order lease, recheck Pending after acquisition, and make confirmation's final save conditional on the locked Pending revision.

## Adjustment and transfer identities change across request retries

This is a **medium, confirmed** idempotency gap in `controllers/stockAdjustmentController.js:114-140` and `controllers/stockController.js:729-763`. Adjustment keys use a newly created adjustment `_id`; transfer keys use a new timestamp/random `transferId`. Retrying after an ambiguous timeout creates different operation keys, so the unique index accepts the full mutation again.

Accept and uniquely persist a stable client/request idempotency key, derive movement keys from it plus stable line identity, and return the prior operation on retry.
