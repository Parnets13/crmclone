# Repeatable Face Punch sessions in Attendance Master

Attendance Master now keeps active employees selectable after a completed session and derives Face Punch In versus Face Punch Out from the employee’s current open-session state. Typed edits clear the selected identity and face match, while both recognition start and punch submission refresh today’s attendance. The backend rejects Punch In when any session is open and closes the most recent open session regardless of punch source. This scoped pass complements the previously approved AttendancePage review and finds no concrete regression in the requested AttendanceMasterPage flow.

Watch for: No blocking regressions remain in the requested repeat Punch In/Punch Out flow.

**Verdict**: APPROVED

## High-level view

The employee API now honors `status=Active`; completed employees remain in the selector, and local search uses the response’s `empId` field alongside name and designation.

Modern sessions are authoritative, with legacy `punchIn`/`punchOut` used only when no sessions exist. Any open session selects Punch Out; after all sessions close, the same employee returns to Punch In indefinitely.

Selection edits, recognition restarts, action mismatches, and successful punches invalidate the prior face match. Attendance refreshes before recognition and before mutation keep the visible label, enabled button, and submitted action aligned.

Backend transition checks scan the full session array rather than only its final entry. Mixed biometric, face, manual, and legacy-web sessions therefore share the same any-open gate.

## One transition state drives every Face Punch gate

`getEmployeeAttendanceState` accepts populated or scalar employee references. A modern open session selects Punch Out, all-closed modern sessions select Punch In, and records without sessions fall back to the equivalent legacy top-level fields. The status message, recognition label, modal action, and both buttons consume this state, so closing one session exposes Face Punch In for the next cycle without removing the employee.

## Selector edits cannot reuse another employee’s face match

The selector no longer excludes completed employees and searches/displays `empId`, matching the employee schema. Typing, clearing, or selecting calls the parent selection handler, which clears the selected ID as appropriate plus the prior match result, score, modal, and recognition status. The API applies the new active-status filter, while the frontend also rejects an explicitly inactive response.

## Revalidation brackets face matching

Recognition opens only after `/attendance/today` succeeds and the previous face result is reset. Submission refreshes again; if the required action changed while the camera was open, the match is cleared and a new verification is required. After a successful write, attendance refreshes before the selection is cleared, so reselecting the employee uses the new session state.

## Mixed-source arrays obey any-open semantics

Punch In refuses to append when any session has an in-time without an out-time. Punch Out searches backward and closes the most recent open session, so a later closed biometric or web session cannot hide an earlier open one. Face-verified marks are stored as `face` and non-face calls as `manual`, without changing the source-agnostic transition rule.

## Focused validation

A six-state matrix passed for no record, modern open, modern closed, legacy open, legacy closed, and an earlier open session followed by a later closed session. Scoped `git diff --check`, backend `node --check`, and frontend ESLint also passed.
