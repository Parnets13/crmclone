# Pending-first stock lifecycle with FIFO readiness and retry-safe movements

The change makes every Sales Order start Pending, treats FIFO readiness as advisory, and reserves stock only during confirmation. Stock quantity is derived from aggregate IN-minus-OUT movements, while GRN inspection, adjustments, transfers, opening stock, invoice reversals, and order transitions use leases and deterministic movement identities. The targeted GRN, FIFO-conflict, duplicate-row, and HTTP-idempotency fixes are present, but interrupted order transitions still expose reservation and expiry races. **Watch for: high, confirmed stock leaks when a partially reserved Pending order is cancelled/rejected/expired; high, confirmed delivered stock restoration after an interrupted delivery; medium, confirmed Pending edits bypassing the order lease; medium, confirmed expiry metadata writers bypassing the shared order lease.**

**Verdict**: NEEDS_CHANGES

## High-level view

Confirmation now resumes from deterministic reservation rows, so an interrupted attempt can leave a Pending order holding real stock. Terminal Pending transitions still assume Pending means unreserved, allowing cancellation, rejection, or expiry to strand those reservations (**high, confirmed**).

Delivery uses a reservation release followed by a permanent delivery OUT. Cancellation calculates outstanding reservation from every SALE OUT and IN rather than movement roles, so a committed delivery followed by a failed status save can be restored as if it were still reserved (**high, confirmed**).

FIFO refresh protects business edits with an `updatedAt` revision and rebuilds the full allocation after conflicts. Generic Pending edits do not acquire `SALES_ORDER:<id>` and do not reject reservation-sensitive changes when an interrupted confirmation has already written rows (**medium, confirmed**).

Actual expiration writers now share `SALES_ORDER:<id>`, but expiry set, extend/reopen, and cancel do not. They can race expiration or confirmation and leave status, `isExpired`, and expiry metadata inconsistent (**medium, confirmed**).

<details>
<summary>Issues (4)</summary>

1. **Partially reserved Pending orders can close without release — High, confirmed** — Cancellation, rejection, and expiry treat Pending as unreserved even though interrupted confirmation can leave reservation OUT rows. Reconcile and release reservations for every terminal transition regardless of status, or block closure until confirmation recovery completes.
2. **Delivery OUT is counted as a reservation — High, confirmed** — Cancellation sums every SALE OUT, so an interrupted delivery can be returned to stock. Calculate outstanding reservation from `RESERVATION` and `RESERVATION_RELEASE` roles only.
3. **Pending edits bypass Sales Order serialization — Medium, confirmed** — Generic edits can change lines while confirmation holds stale stock-key leases or while partial reservations exist. Acquire the order lease before reading keys and forbid reservation-sensitive edits whenever reservation rows exist.
4. **Expiry metadata writers bypass the order lease — Medium, confirmed** — Set, extend/reopen, and cancel-expiry can race leased expiration/status transitions. Put every expiry writer under `SALES_ORDER:<id>` and use lifecycle/revision predicates.

<summary>Details</summary>

## Interrupted confirmation can leave terminal Pending orders holding stock

The recovery branch treats any `RESERVATION` row as an interrupted confirmation and continues only missing line reservations (`controllers/salesOrderController.js:1404-1412`, `1609-1645`). Partial reservation rows are therefore a supported state: the order remains Pending while one or more OUT movements reduce available stock.

Cancellation and rejection release only when `originalStatus` is Confirmed, Processing, or In Transit; Pending takes the “no reserved stock” branch (`controllers/salesOrderController.js:1785-1863`). Manual and automatic expiry also update any Pending order without checking or releasing reservation rows (`controllers/salesOrderController.js:4195-4257`, `4678-4730`; `cron/salesOrderExpiration.js:78-114`). **High, confirmed:** cancelling, rejecting, or expiring after an interrupted multi-line confirmation leaves the committed reservation active indefinitely. Deletion already detects this state at `controllers/salesOrderController.js:2989-3004`.

Centralize terminal reconciliation under the order and stock-key leases. Compute outstanding quantity from `RESERVATION` minus `RESERVATION_RELEASE` rows regardless of current status, append deterministic final releases, then persist Cancelled/Rejected/Expired; alternatively, block terminal transitions with `PENDING_ORDER_HAS_STOCK_RESERVATION` until confirmation recovery finishes.

## Cancellation can reverse a delivery that committed before its status save

Delivery appends an IN `RESERVATION_RELEASE` and an OUT `DELIVERY` before saving Delivered (`controllers/salesOrderController.js:1735-1782`, `1923`). If the save fails after both movements, aggregate stock correctly reflects the delivery while status remains Confirmed.

Cancellation queries every SALE OUT and IN (`controllers/salesOrderController.js:1793-1804`). **High, confirmed:** the delivery OUT is added to `blockedQuantity`, causing `FINAL_RELEASE` to return physically delivered stock. A reservation of 10 followed by delivery release 10 and delivery OUT 10 becomes `20 OUT - 10 IN = 10` restored, although no reservation remains.

Filter blocked quantity to `movementRole: 'RESERVATION'` and released quantity to `movementRole: 'RESERVATION_RELEASE'`; `DELIVERY` must remain outside reservation reconciliation.

## Pending edits do not participate in confirmation serialization

The status endpoint selects product keys before acquiring `SALES_ORDER:<id>` and stock leases, then rereads the order inside the lock (`controllers/salesOrderController.js:2091-2121`). Generic edit acquires no order lease, allows reservation-sensitive edits while status is Pending, and mutates with only `{ _id, status }` (`controllers/salesOrderController.js:2293-2355`, `2768-2783`).

**Medium, confirmed:** an edit can commit after confirmation selected its keys, making confirmation reserve edited keys without their leases or reserve the old lines while the order now contains new ones. An interrupted-confirmation order can also replace lines whose operation keys already exist; recovery then skips those old rows and confirms movements that no longer match the order.

Acquire `SALES_ORDER:<id>` before reading products in both paths, reread under that lease, then acquire the required sorted stock-key union. Reject reservation-sensitive edits whenever active reservation rows exist, even while Pending, and use an `updatedAt` predicate for the final edit.

## Expiry metadata writers can conflict with leased lifecycle transitions

`expireOrderNow`, HTTP auto-expiry, and cron expiry acquire `SALES_ORDER:<id>` (`controllers/salesOrderController.js:4195-4257`, `4678-4730`; `cron/salesOrderExpiration.js:78-114`). `setOrderExpiry`, `extendOrderExpiry`, and `cancelOrderExpiry` read and save without it (`controllers/salesOrderController.js:4034-4088`, `4107-4168`, `4350-4386`); extension can also reopen Expired or Cancelled to Pending.

**Medium, confirmed:** an extender can load Pending, expiration can commit, and the later extension can set a future date plus `isExpired: false` while status remains Expired. Set/cancel can similarly commit expiry metadata after confirmation changed the order out of Pending, yielding accepted but non-actionable expiry state.

Acquire `SALES_ORDER:<id>` before every expiry read and mutate with status plus revision predicates. Reopening Expired should rebuild FIFO readiness after the leased state change; set/cancel should reject when the locked status is no longer Pending.
