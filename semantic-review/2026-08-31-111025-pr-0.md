# Independent combined level cap across CRM and Sales Executive ordering

The change separates the arithmetic sum of selected level rates from the existing reducing-basis master cap across CRM Sales Orders, Dealer Invoices, and Sales Executive order requests. Live backend flows reconstruct direct, level, and dealer-extra stages from authoritative mappings, while Sales Order and linked-invoice replay use persisted ordered stages and cap snapshots. Direct and dealer-extra stages are excluded from `combinedLevelDiscountCap`, but mapping persistence, strict backend enforcement, and the SE request handoff still have shipping defects.

Watch for: **confirmed (high)** optional cap fields reject `null` and break direct-sales and purchase mapping saves; **confirmed (medium, security/correctness)** the authoritative policy accepts level totals up to 0.01 percentage points above the cap; **confirmed (high)** approved SE requests are converted with current mappings instead of their submission-time policy; **confirmed (medium, UX/compatibility)** mobile final validation uses stale cart caps and blocks legacy carts; **confirmed (medium)** no focused regression tests cover these boundaries.

**Verdict**: NEEDS_CHANGES

## High-level view

`validateDiscountPolicy` is the common enforcement point for CRM live pricing, Sales Order replay, Dealer Invoice replay/pre-save, and SE calculation/final submission. Its default tolerance turns the required hard arithmetic maximum into a cap-plus-0.01 rule across every backend caller.

The mapping controller stores `null` when a cap does not apply, but the schema treats optional `null` values as invalid numbers. This prevents otherwise valid direct-sales and purchase mappings from saving.

Sales Orders and linked Dealer Invoices persist ordered stages and use legacy `maxDiscountPercentage` as a fallback for the new level-only cap. SE order requests persist only scalar results; conversion omits those values and fetches the current mapping, leaving this historical handoff outside the snapshot model.

Mobile recalculation receives current server caps, but final validation reads the separately persisted cart. Mapping changes and pre-upgrade carts therefore produce stale or missing-cap errors before authoritative submission.

1. **Optional cap nullability — confirmed (high)** — `Number.isFinite` rejects explicit `null`, so direct-sales mappings fail the combined-cap validator and purchase mappings fail both cap validators. Allow null for non-applicable fields or omit those fields before persistence.
2. **Backend level-cap overage — confirmed (medium, security/correctness)** — The shared backend accepts totals through `cap + 0.01`, violating the strict arithmetic maximum. Compare at supported precision without a one-basis-point allowance.
3. **SE request snapshot gap — confirmed (high)** — Approved requests are converted using the current mapping rather than submission-time ordered stages and caps. Persist and replay a complete request-line policy/permission snapshot, with repricing explicit.
4. **Stale mobile cart caps — confirmed (medium, UX/compatibility)** — Server-refreshed caps do not update the cart used by final validation, and old carts have only `maxDiscountPercentage`. Reconcile server results into persisted cart state and migrate/fallback legacy combined caps.
5. **No cap regression coverage — confirmed (medium)** — No automated tests exercise schema nullability, strict boundaries, snapshot conversion, or stale carts. Add focused policy, schema/controller, handoff, and mobile tests.

## Optional cap validators make non-level mappings unsavable

This is **confirmed (high)** in `discountMappingSchema` (`crm_backend/models/DiscountMapping.js:107-128`). Both custom validators are bare `Number.isFinite` functions. Mongoose invokes them for explicit `null`, even though `combinedLevelDiscountCap` is optional for direct mappings and both caps are optional for purchase mappings. `createDiscountMapping` always includes `masterDiscountCap: parsedMasterCap` and `combinedLevelDiscountCap: parsedCombinedLevelCap` (`crm_backend/controllers/discountMappingController.js:211-240`, `385-388`), with non-applicable values set to `null`; the CRM form also submits a null combined cap for direct sales mappings (`src/Sales&Purchase/DealerDiscountManagement.jsx:3408-3413`).

A `validateSync` probe produced the combined-cap finite-number error for a valid direct-sales mapping with a master cap, and both finite-number errors for a purchase mapping. New direct-sales mappings, edits that clear their non-applicable level cap, and purchase mappings fail before persistence. Make the validators accept `null`/`undefined` when the field is not required, or omit non-applicable fields; retain conditional required validation for level-capable sales mappings.

## Shared backend policy permits a one-basis-point overage

This is **confirmed (medium, security/correctness)** in `validateDiscountPolicy` (`crm_backend/utils/sequentialDiscountPolicy.js:148-195`). The function defaults `tolerance` to `0.01` and reports a violation only when `levelDiscountTotalPercentage > normalizedCombinedLevelCap + tolerance`. A policy probe with cap 10 accepted 10.005 and 10.01, rejecting only 10.010001.

CRM Sales Order live/replay, Dealer Invoice live/linked/pre-save, and SE calculation/final submission all delegate to this utility. Browser and mobile checks use approximately `0.000001`, but an API caller bypassing those clients receives backend acceptance above the configured cap. Compare normalized precision values directly, or use an epsilon smaller than the supported input precision.

## Approved SE requests lose submission-time policy at conversion

This is **confirmed (high)** across `createOrderRequest`, `requestProductSchema`, and the CRM prefill flow. Final SE submission resolves live mappings and validates both caps server-side, but persists only scalar outcomes (`crm_backend/SalesExecutiveAppBackend/controllers/orderRequestController.js:61-181`; `crm_backend/models/DealerOrderRequest.js:19-40`). It does not persist `orderedStages`, a mapping version, or the permission snapshot used for validation.

The conversion endpoint returns selected/manual levels and a mapping ID but not the stored caps (`crm_backend/controllers/dealerOrderRequestController.js:getPrefillData`, lines 387-402). `SalesOrderDashboard` fetches applicable discounts again (`src/Sales&Purchase/SalesOrderDashboard.jsx:842-988`), and the Sales Order canonicalizer independently queries the current mapping (`crm_backend/controllers/salesOrderController.js:75-205`). A mapping or cap change after approval can make the request unconvertible or price it under a policy different from the one reviewed.

Persist canonical ordered stages, both caps, mapping identity/version, and permission context on each request line. Conversion should replay that snapshot by default and require explicit repricing to adopt current policy.

## Mobile final validation reads stale cart policy

This is **confirmed (medium, UX/compatibility)** in `OrderCartScreen`. `calculateSummary` merges current backend item data into `orderSummary.items` but does not update or persist `cart` (`src/screens/Orders/OrderCartScreen.jsx:442-475`). `handleManualLevelChange` and `handlePlaceOrder` calculate validity from `cart` and read only `item.masterDiscountCap` / `item.combinedLevelDiscountCap` (`OrderCartScreen.jsx:538-600`, `613-659`).

A mapping change after adding an item leaves the final gate on the old cap: a stale tighter value blocks a valid order, while a stale looser value proceeds only to backend rejection. Existing AsyncStorage carts from the prior build contain `maxDiscountPercentage`, but `calcItemDiscount` has no legacy fallback (`OrderCartScreen.jsx:55-60`), so discounted legacy lines are treated as missing caps. Reconcile API items into the persisted cart, or make final validation a server operation; migrate/fallback legacy values for the combined-level cap.

## Cap boundaries and handoffs lack regression tests

This is **confirmed (medium)**: no test invokes `validateDiscountPolicy` or asserts `combinedLevelDiscountCap`, and the backend package has no test script. The CRM production build and backend syntax checks pass, but they do not exercise schema validation, arithmetic boundaries, snapshot conversion, or stale carts.

Add policy tests at the exact cap and smallest supported increment above it, schema tests for direct-sales/purchase nullability, controller tests for live and snapshot fallback paths, an SE request-to-Sales Order snapshot test, and mobile tests for legacy and server-refreshed carts.
