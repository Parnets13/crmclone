# Safety-gated Shree Jain transaction reset

The revised script defaults to dry-run, hard-codes the Shree Jain tenant key, binds live execution to exact deletion-plan fingerprints, and verifies the reset inside a snapshot transaction before commit. It now retains only completed legacy Opening Stock adjustments, preserves DealerPricing provenance, and hashes protected master content while excluding only fields intentionally reset. The accepted preservation boundary is still violated by the journal and voucher predicates, and several datasets described as preserved are not included in the before/after hashes.

Watch for: **confirmed** expense, TDS, and depreciation journals are deleted solely because they are auto-generated; **confirmed** retained bank reconciliations are left pointing to deleted vouchers; **confirmed** manual journals and completed legacy adjustments are not content-fingerprinted.

**Verdict**: NEEDS_CHANGES

## High-level view

Dry-run is the default and `--apply` requires the fixed confirmation, backup and maintenance attestations, exact database name, and the currently recomputed manifest fingerprint. Full-delete and selective-delete plans hash complete documents, then are recomputed inside a transaction with snapshot read concern before the first delete.

Protected products, users, listed masters, DealerPricing rows, dealer opening fields, opening ledgers and journals, and opening-stock quantity/rate are hashed before and after the reset. Approved derived fields such as dealer allocation totals, ledger running balances, stock movement balance, and bank/cash current balances are the only omissions within those covered datasets.

The journal partition still treats every auto-generated non-opening journal as transactional. Expense, TDS, and depreciation workflows create `referenceType: Manual` journals with `isAutoGenerated: true`, so their source records survive while their accounting entries are deleted.

Bank reconciliation documents are untouched, but their `clearedItems` map is keyed by voucher ID and the script fully deletes `vouchers`. Exact document preservation therefore leaves reconciliation state referring to records that no longer exist.

The server-stop and backup gates are operational attestations rather than enforced locks. Given the stated architecture constraint, they are adequate only for a controlled testing reset where every API, worker, cron process, and alternate writer is independently confirmed stopped and the backup has been restore-tested; they are not a production-safe concurrency boundary.

## Exact deletion plans and transaction-bound acceptance

The full-delete manifest fingerprints every sorted document in each target collection, and the selective plan does the same for dealer/supplier ledgers, transaction journals, non-opening stock movements and adjustments, transaction notifications, and GRN counters. `assertPlanUnchangedInTransaction` recomputes those hashes and the covered preservation snapshot through the transaction session before any writes; `withTransaction` uses snapshot read concern and majority write concern (`resetShreeJainTransactions.mjs:720-948`).

`verifyResetState` checks full/selective emptiness, dealer derived-state resets, opening ledger and stock balances, bank/cash opening balances, and covered preservation hashes before commit (`resetShreeJainTransactions.mjs:982-1131`). The same verification runs after commit as a read-back smoke check (`resetShreeJainTransactions.mjs:1188-1197`). DealerPricing is only read and hashed; the prior provenance rewrite is gone.

Only `reason: "Opening Stock", status: "Completed"` adjustments contribute linked stock movement references, and malformed completed openings block apply (`resetShreeJainTransactions.mjs:201-206, 308-320, 425-445`). Canonical Price List opening rows are retained by their opening markers, and the opening-stock hash excludes only derived `balance`, preserving quantity and rate. Product and price-list history documents are fully hashed through `PROTECTED_COLLECTIONS`.

## Auto-generated accounting journals cross the reset boundary

This is **confirmed** at `resetShreeJainTransactions.mjs:206-224`: `TRANSACTION_JOURNAL_FILTER` matches any non-Opening Entry with `isAutoGenerated: true`, even when its reference is not one of the approved sales/purchase/payment types. Expense posting creates a `referenceType: Manual`, auto-generated journal (`accountingService.js:448-463`); both TDS deduction and deposit do the same (`tdsController.js:69-87, 156-174`); annual depreciation does so as well (`fixedAssetController.js:252-269`). Their source records are not deleted, leaving surviving business records without their posted journal entries.

Remove the blanket `isAutoGenerated: true` branch. Require approved transaction provenance such as DealerInvoice, SupplierInvoice, DealerPayment, SupplierPayment, SalesOrder, PurchaseOrder, or a separately reviewed voucher link, and report each preserved journal class in dry-run output.

## Preserved accounting and legacy-opening content is outside the hashes

This is **confirmed** because `snapshotProtectedState` hashes only `PROTECTED_COLLECTIONS` plus projected opening datasets (`resetShreeJainTransactions.mjs:456-529`). Manual non-opening journals are only counted, completed legacy adjustments are represented only by a count, and `expenses`, `tdsentries`, `financialyearclosings`, `yearendchecklists`, and `bankreconciliations` do not appear in the protected list. Pre-commit and post-commit comparisons therefore cannot prove their exact preservation.

`getLegacyOpeningAdjustments` reads a projection for validation, but the manifest stores only `legacyOpeningAdjustments.length` (`resetShreeJainTransactions.mjs:308-320, 612`). A completed opening adjustment can change non-key content without changing either the deletion fingerprint or manifest fingerprint. Add full-document hashes for every retained journal and completed legacy adjustment, and add the explicitly preserved accounting collections to the protected snapshot.

## Retained bank reconciliations point to fully deleted vouchers

This is **confirmed** because `vouchers` is an unconditional full-delete collection (`resetShreeJainTransactions.mjs:129-133`), while `BankReconciliation.clearedItems` maps voucher IDs to clearance metadata (`models/BankReconciliation.js:21-39`). Leaving the reconciliation document unchanged does not preserve usable reconciliation state after its referenced vouchers disappear.

Preserving reconciliations requires retaining and fingerprinting the referenced voucher rows or explicitly migrating the reconciliation representation in the same transaction. Clearing reconciliation data would contradict the requested exact-preservation boundary.

## Number sources reset only where the namespace is fully deleted

The GRN counter predicate exactly matches the `grn-YYYYMMDD` IDs used by `Counter.getNextSequence` (`resetShreeJainTransactions.mjs:238`; `grnController.js:35-38`). Other fully deleted transaction collections derive their next number from remaining documents, so their sequences restart after deletion.

Journal numbering is **confirmed** not to restart generally: monthly `JV-YYYYMM-*` generation scans surviving JournalVoucher rows and increments the maximum (`accountingService.js:42-62`; `tdsController.js:26-38`). This avoids collisions while opening and unrelated journals remain, but means “transaction numbering reset” cannot include the shared journal namespace. State that journal numbers continue, or define a separate non-colliding migration.

## Manual quiescence is acceptable only for isolated testing

The missing app-wide lock and independent tenant sentinel remain **confirmed** architectural limitations. `--maintenance-confirmed` and `--backup-confirmed` are booleans, while the database assertion compares the connection against the configured Shree Jain mapping (`resetShreeJainTransactions.mjs:54-61, 694-703, 1140-1148`). The snapshot recheck blocks a stale reviewed plan but cannot stop a new write after the snapshot; the post-commit check can detect such a survivor only after destructive work commits.

For this testing-only script, the gates are adequate only as a runbook boundary: stop every server, worker, cron runner, and ad-hoc writer; independently verify the displayed target; restore-test the fresh backup; then use the exact dry-run manifest. Production use still requires enforceable quiescence and independent identity.

## Destructive rollback paths remain untested

This is **confirmed** from the change set: the only changed artifact is the untracked script and no replica-set integration test accompanies it. Static syntax validation passed with `node --check`, but no executable test proves stale-manifest refusal, rollback on pre-commit verification failure, exact preserve/delete partitioning, or post-commit smoke behavior.
