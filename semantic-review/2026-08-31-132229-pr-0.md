# Stock lifecycle final gate after synchronization fixes

The stock lifecycle changes align terminal display, Pending-ready presentation, the Stock Arrived queue, generic edits, expiry reopening, and legacy transition reporting around the aggregate stock summary. Generic edits now remove client-authored lifecycle fields, force product stock recalculation, and reject an empty replacement product list; aggregate refresh also treats zero lines as waiting rather than ready. One synchronization path remains incomplete: the new scheduled expiry job transitions a ready order to `Expired` without clearing its compatibility `stockAvailable` flag. Watch for: **confirmed** scheduled expiry leaves `stockAvailable: true` on orders that have left the actionable queue.

**Verdict**: NEEDS_CHANGES

## High-level view

The frontend derives terminal N/A and Pending-ready presentation from status plus the aggregate summary, while the backend Stock Arrived list and count use the same Pending, non-expired, historically out-of-stock, currently-ready predicate.

Generic product updates strip submitted lifecycle fields, reject empty product arrays, and force stock recalculation. Expiry extension similarly reopens eligible orders to Pending and immediately recalculates stock.

**Confirmed:** manual expiry and the legacy controller expiry loop clear `stockAvailable`, but the newly scheduled multi-company expiry job updates only `isExpired`, `expiredAt`, and `status`. A previously ready order therefore remains persisted with `stockAvailable: true` after becoming terminal.

## Scheduled expiry leaves the compatibility readiness flag set

This is **confirmed** in `crm_backend/cron/salesOrderExpiration.js:81-89`. The bulk update changes a Pending order to `Expired` and sets expiry metadata but omits `stockAvailable: false`. The two controller-managed expiry paths explicitly clear that flag in `salesOrderController.js:4187` and `salesOrderController.js:4465`, and normal status changes also clear it when leaving Pending.

The Stock Arrived query and terminal UI exclude the expired order, but the persisted lifecycle state remains contradictory. Any legacy consumer that reads `stockAvailable` directly continues to treat the expired order as ready. Add `stockAvailable: false` to the scheduled expiry `$set` so every terminal transition maintains the same invariant.

</details>
